## 2. Posture summary
The code has no injection or memory-safety problems and no secrets. History is clean: no keys, tokens or keystores were ever committed. Packet parsers check lengths before every read, process launches are quoted with no shell, the release pipeline is SHA-pinned and least-privilege, and all radio/TTS text built on the PC comes from fixed templates.

The weakness is **design-level: nothing on the LAN is authenticated.** Any host on the same (Private) network can:
- drive the virtual pad;
- capture or redirect the phone's dashboard;
- redirect the phone to itself;
- make the phone speak arbitrary text.

Comparable LAN pad-mapper and phone-controller tools accept the same model. Since the firewall rule limits exposure to networks Windows considers Private, real-world risk is low on a home network and higher on shared flats or dorms. There is also one input-validation bug: a single crafted telemetry packet can stop the dashboard and radio for the session.

### 1. Any LAN host can inject control packets that drive the virtual Xbox 360 pad

**Fingerprint:** `F1Controller/Transport/UdpReceiver.cs:ReceiveLoop:unauthenticated-control-pad-injection`

The UDP control listener on :5555 (new UdpClient(port), IPv4 any address) treats any non-ping datagram of 18 bytes or more as phone input. There is no pairing, shared secret, auth field or source-address binding: the sender endpoint is stored in _phoneEndPoint for replies but never compared. The sequence filter is one global counter that drops only deltas in (-1000, 0] and treats any jump of 1000 or more in either direction as a counter reset, so a second host's packets are accepted interleaved with the real phone's without knowing its sequence number. Accepted packets go straight to XInputController.Submit, which writes steering, both triggers and all 14 buttons to the ViGEm virtual pad and calls SubmitReport. An attacker who knows or sniffs the phone's current sequence P can send P+999 to make the phone's next ~998 packets look stale. The installer's firewall rule (inbound UDP for FullLock.exe, Private profile, no remote-address restriction) is the only visible control. Impact is limited to the user's game input while phone mode is running, consistent with the LAN-UDP baseline of comparable pad-mapper tools.

**Claimed root cause:** UdpReceiver.RunAsync never binds control input to an authenticated or paired peer: the source endpoint is recorded but never checked, ControlPacket has no authentication field, and the sequence check is global rather than per peer and accepts any |delta| >= 1000 as a reset.

**Trace**
- entrypoint `windows-receiver/F1Controller/Transport/UdpReceiver.cs:82` (UdpReceiver.RunAsync): new UdpClient(_port) binds UDP :5555 on all IPv4 interfaces
- propagation `windows-receiver/F1Controller/Transport/UdpReceiver.cs:138` (UdpReceiver.RunAsync): Any non-ping datagram of 18+ bytes is parsed with no source check
- propagation `windows-receiver/F1Controller/Transport/UdpReceiver.cs:146` (UdpReceiver.RunAsync sequence filter): Global signed delta against the last accepted sequence from any sender; |delta|>=1000 is accepted as a reset
- propagation `windows-receiver/F1Controller/Transport/UdpReceiver.cs:196` (UdpReceiver.RunAsync): OnPacketReceived fires with the attacker's packet
- propagation `windows-receiver/F1Controller/Program.cs:177` (Program.Main OnPacketReceived handler): xinput.Submit(packet, receiveTicks) with no further checks
- sink `windows-receiver/F1Controller/Controller/XInputController.cs:109` (XInputController.SubmitLocked): Packet steer, triggers and buttons are written to the ViGEm virtual pad and SubmitReport() is called

**Evidence**
- `windows-receiver/F1Controller/Transport/UdpReceiver.cs:119`: The remote endpoint is recorded for every datagram but never compared to a paired peer
- `windows-receiver/F1Controller/Transport/UdpReceiver.cs:147`: Only deltas in (-1000,0] are dropped; all other sequences from any sender are accepted
- `windows-receiver/F1Controller/Transport/PacketParser.cs:143`: Parse validates length only; the 18-byte layout has no authentication field
- `windows-receiver/F1Controller/Controller/XInputController.cs:56`: Submit's only gate is IsConnected (virtual pad plugged in)
- `installer/FullLock.iss:52`: Firewall rule: inbound UDP for FullLock.exe on the Private profile with no remoteip restriction (strongest visible control)

**Blockers**
- No OS-enforced sandbox on this host, so the receiver harness was not run and no observed result exists (source-only review cannot confirm)
- Whether the user's network is classified Private and contains untrusted hosts is a deployment fact outside the source

**Validation plan**
- Local: In an approved sandbox with no external network and ViGEm replaced by a recording stub (or XInputController not connected and OnPacketReceived observed directly), start UdpReceiver on a loopback test port. From socket A send an 18-byte packet seq=1 steer=0; from socket B send seq=100000 steer=32767; then from A send seq=2 steer=0. Assert all three fire OnPacketReceived (the last two as resets), that LastPacket.Steer toggles accordingly, and that the receiver's _phoneEndPoint ends as socket A. Non-destructive; no real pad or game involved.
- Owner check: The owner runs 'netsh advfirewall firewall show rule name=FullLock verbose' to confirm Profile=Private, RemoteIP=Any, and checks whether the network used for phone mode is classified Private and shared with untrusted clients (guests, IoT devices). Read-only checks; do not send packets to the user's live PC while a game is running.

### 2. Any datagram redirects the phone telemetry and radio stream to an arbitrary host

**Fingerprint:** `F1Controller/Transport/UdpReceiver.cs:_phoneEndPoint:any-datagram-reply-target-hijack`

UdpReceiver.RunAsync sets _phoneEndPoint from every datagram received on UDP :5555, including a 1-byte datagram, before the ping check (line 122), the length check (line 135) and the sequence filter. SendToPhone checks only that _client and _phoneEndPoint are non-null and that IsReceiving is true. IsReceiving tracks the last valid control packet from any source, so the real phone keeps it true. Game-state and race-state datagrams (Program.cs:164,170) and the 3x-repeated radio calls (RadioSender.cs:46) all go to whichever endpoint sent the most recent datagram. A LAN peer that sends small datagrams faster than the phone's ~250 Hz control stream receives a large share of these event-driven sends, and the phone loses that share of its dashboard and radio. With a spoofed source address, those datagrams go to a third-party victim instead. Source shows no reply amplification: pongs echo only to the ping's own sender and outbound datagrams are small. The only control is the installer's Private-profile firewall rule; the app does no peer binding. Impact is low and limited to the home LAN, which matches the comparable baseline (unauthenticated LAN UDP pad mappers). Whether the attacker actually wins the race is a runtime fact.

**Claimed root cause:** The reply target is taken from the latest datagram of any shape and any source, not from the last valid control packet of a bound or paired peer.

**Trace**
- entrypoint `windows-receiver/F1Controller/Transport/UdpReceiver.cs:104` (UdpReceiver.RunAsync): Receives any datagram on UDP :5555, bound on all interfaces (line 82)
- propagation `windows-receiver/F1Controller/Transport/UdpReceiver.cs:119` (UdpReceiver.RunAsync): _phoneEndPoint = result.RemoteEndPoint runs before the ping, size and sequence checks
- propagation `windows-receiver/F1Controller/Transport/UdpReceiver.cs:211` (UdpReceiver.SendToPhone): The only gate is IsReceiving, which valid control packets from the genuine phone (or any source) keep true
- propagation `windows-receiver/F1Controller/Program.cs:164` (Program.Main telemetry.OnStateChanged handler): Game state goes out via receiver.SendToPhone (race state at line 170)
- sink `windows-receiver/F1Controller/Transport/RadioSender.cs:46` (RadioSender.Send): Radio call datagrams (3 repeats, 30 ms apart) go to the current _phoneEndPoint

**Evidence**
- `windows-receiver/F1Controller/Transport/UdpReceiver.cs:119`: Unconditional overwrite of the reply endpoint from any datagram
- `windows-receiver/F1Controller/Transport/UdpReceiver.cs:135`: The length check runs only after the overwrite
- `windows-receiver/F1Controller/Transport/UdpReceiver.cs:63`: IsReceiving depends only on the time since the last valid control packet, with no source binding
- `windows-receiver/F1Controller/Transport/UdpReceiver.cs:215`: client.Send(data, data.Length, phone) sends to the hijacked endpoint

**Blockers**
- No OS-enforced sandbox exists on this host, so no loopback harness could be run. The share of SendToPhone datagrams an attacker wins against a 250 Hz phone stream is a runtime race outcome.
- Whether untrusted hosts share the Private-profile network segment with the PC is a deployment fact.

**Validation plan**
- Local: In a sandbox with only loopback networking: start UdpReceiver on a test port. Socket A sends valid 18-byte control packets with increasing sequence numbers every 4 ms. Socket B sends a 1-byte datagram right after each of A's packets. Call SendToPhone with a marker payload 100 times at random intervals while asserting IsReceiving stays true. Count the markers received by A and by B. B receiving any marker confirms the redirect. Non-destructive, no game or ViGEm needed.
- Owner check: The owner checks whether any untrusted or guest host can reach UDP 5555 on the PC while phone mode runs on a network marked Private, for example from a second device sending one datagram and watching for game-state datagrams back during a session.

### 3. Any LAN host can redirect and persist the phone's control-server address with a forged discovery beacon

**Fingerprint:** `android/network/DiscoveryListener:unauthenticated-beacon-server-redirect`

The phone binds UDP 0.0.0.0:5556 and accepts any datagram that starts with the static bytes FB FF FF FF 'F1RX' followed by a u16 port. It takes the PC's IP from the datagram's source address. The beacon carries no secret or authentication. MainActivity.onReceiverFound acts on the beacon whenever transport.state.isConnected is false, meaning no pong in the last LINK_TIMEOUT. That is true before the transport starts, from connect() until the first pong is seen, and whenever the link drops. When it acts, it overwrites serverIp/serverPort, saves them to SharedPreferences, and restarts the transport toward the sender. The phone's receiveLoop accepts a pong (PING marker, at least 16 bytes) from any source and sets lastPongNs. So once redirected, the attacker can hold isConnected=true by echoing pings, and the real PC's beacons then stop switching the phone back. Result: the user's steering/pedal stream goes to the attacker, who learns the phone's ephemeral port. The attacker can also feed forged game-state and radio packets, and the phone won't reach the real receiver until the user intervenes or the attacker stops answering. Scope is the same LAN segment. This is comparable to typical unauthenticated phone-as-controller LAN apps.

**Claimed root cause:** Server selection trusts an unauthenticated broadcast. decodeDiscovery checks only a static marker/tag (DiscoveryListener.kt:76-82), the datagram source becomes the new serverIp (DiscoveryListener.kt:55), and shouldSwitchServer gates only on the locally computed isConnected flag (DiscoveryListener.kt:94). That flag is false at session start and is driven by pongs accepted from any source (UdpTransport.kt:327).

**Trace**
- entrypoint `android/app/src/main/java/com/f1controller/network/DiscoveryListener.kt:53` (DiscoveryListener.listenLoop): Receives any datagram on a socket bound to 0.0.0.0:5556 (bind at line 48); there is no source filter
- propagation `android/app/src/main/java/com/f1controller/network/DiscoveryListener.kt:76` (decodeDiscovery): Checks only length >= 10, the static marker 0xFFFFFFFB and the 'F1RX' tag, then returns the attacker-chosen u16 port
- propagation `android/app/src/main/java/com/f1controller/network/DiscoveryListener.kt:55` (DiscoveryListener.listenLoop): Server IP is taken from the datagram source address and passed to onFound
- propagation `android/app/src/main/java/com/f1controller/network/DiscoveryListener.kt:94` (shouldSwitchServer): Switches whenever !connected and the IP or port differs
- propagation `android/app/src/main/java/com/f1controller/network/UdpTransport.kt:172` (UdpTransport.connect): Each session starts with TransportState(isActive = true), so isConnected is false until a pong arrives
- sink `android/app/src/main/java/com/f1controller/MainActivity.kt:175` (MainActivity.onReceiverFound): Overwrites transport.serverIp/serverPort with the beacon sender's values, saves them to SharedPreferences (lines 177-180), and restarts the transport toward the attacker (lines 182-185)

**Evidence**
- `windows-receiver/F1Controller/Transport/DiscoveryBeacon.cs:32`: The legitimate beacon is built once from static bytes plus the control port; it has no secret, nonce or signature
- `android/app/src/main/java/com/f1controller/MainActivity.kt:115`: discovery.start() runs right after the optional transport.connect(), so beacons are processed during the pre-pong window
- `android/app/src/main/java/com/f1controller/network/UdpTransport.kt:238`: isConnected is just System.nanoTime() - lastPongNs < LINK_TIMEOUT_NS
- `android/app/src/main/java/com/f1controller/network/UdpTransport.kt:327`: A pong from any source address (PING marker, >= 16 bytes, sentUs not validated) sets lastPongNs, which lets an attacker hold the link up

**Blockers**
- No OS-enforced sandbox or emulator is available, so no target code was run. The redirect, its persistence, and the pong-hold were not observed at runtime.
- Whether a given device's Wi-Fi power saving delivers unicast/broadcast datagrams to port 5556 during the pre-pong window is a device/runtime fact that source cannot settle

**Validation plan**
- Local: On an isolated emulator or a test LAN with dummy hosts only: start the app with any server IP. From a second host, send the 10-byte payload FB FF FF FF 46 31 52 58 <port u16 LE> as unicast to phone:5556 at about 10-50 Hz. Check that the Settings screen and /data/data/com.f1controller/shared_prefs show server_ip set to the second host. Capture the phone's ping datagrams on the second host and echo each one back unchanged to the source port, then confirm the UI shows connected. Start the real receiver's beacon and confirm the phone stays on the second host. Stop there. Do not inject game-state or radio packets.

### 4. Phone accepts radio/TTS, pong and dashboard datagrams from any LAN host, not only the configured receiver

**Fingerprint:** `android/network/UdpTransport:receiveLoop-no-source-binding`

The phone's UDP socket is unconnected, and receiveLoop never checks that a datagram came from serverIp:serverPort. A LAN host that can reach the phone's ephemeral source port can send a 0xFFFFFFFC radio datagram. The phone then speaks attacker-chosen text (up to 255 bytes in a 256-byte buffer) with vibration and a banner, as long as engineer chattiness is not Off. Priority 3 flushes lesser queued speech. The same host can also forge pongs, which mark the link live for 1 s each and so suppress the discovery fallback, and can overwrite the game and race dashboards. The attacker learns the port from the phone's outbound packets or by sweeping ports. Scope is the home LAN, consistent with comparable LAN controller apps.

**Claimed root cause:** UdpTransport.connect creates an unconnected DatagramSocket (UdpTransport.kt:163), and receiveLoop (UdpTransport.kt:286-334) dispatches on the marker without comparing recvPacket.address/port with the resolved server address. The protocol has no message authentication.

**Trace**
- entrypoint `android/app/src/main/java/com/f1controller/network/UdpTransport.kt:293` (UdpTransport.receiveLoop): socket.receive accepts a datagram from any source address and port
- propagation `android/app/src/main/java/com/f1controller/network/UdpTransport.kt:299` (UdpTransport.receiveLoop): The radio-marker branch decodes the datagram with no sender check
- propagation `android/app/src/main/java/com/f1controller/network/RadioPacket.kt:24` (decodeRadioCall): Text, priority and category come straight from the attacker's bytes
- propagation `android/app/src/main/java/com/f1controller/network/UdpTransport.kt:337` (UdpTransport.onRadioCall): The repeat filter keys only on the attacker-chosen callId, then the call is emitted
- propagation `android/app/src/main/java/com/f1controller/MainActivity.kt:113` (MainActivity.onCreate): The radio flow is collected into engineerRadio.play
- sink `android/app/src/main/java/com/f1controller/engineer/EngineerRadio.kt:151` (EngineerRadio.speak): tts.speak(call.text); priority 3 uses QUEUE_FLUSH when no other critical call is in flight

**Evidence**
- `android/app/src/main/java/com/f1controller/network/UdpTransport.kt:163`: DatagramSocket() is created and never connect()ed to the server
- `android/app/src/main/java/com/f1controller/network/UdpTransport.kt:327`: A ping-marker datagram from any source sets lastPongNs, so isConnected (line 238) is true for 1 s

**Blockers**
- No OS-enforced sandbox, device or emulator was available, so the end-to-end TTS, banner and vibration effect was not observed

**Validation plan**

From a second host, send one datagram to that phone IP and port with hex bytes FC FF FF FF 39 30 03 07 05 followed by ASCII 'hello'. Expected: the phone shows a banner, vibrates and speaks 'hello'. Also send a 16-byte ping-marker datagram (FF FF FF FF plus 12 bytes) and confirm the status shows 'Receiver responding' while the real receiver is stopped. Regression: once the socket is connect()ed to the server address (or the sender is compared with addr:port), the same datagrams are ignored.

### 5. One spoofed F1 2021 Lap Data datagram with an infinite or huge lapDistance can kill the telemetry receive loop

**Fingerprint:** `fulllock/RaceTracker.Process/lapdist-bin-overflow-unhandled-telemetry-loop`

RaceTracker.Process turns the attacker-controlled f32 lapDistance of the player's Lap Data entry into an array index with an unchecked float-to-int cast, (int)(lapDist / 10f). The guard checks lapDist >= 0 and bin < 999 but never bin >= 0. NaN fails the lapDist >= 0 test and is safe. For +Infinity, or finite values of about 2.15e10 or more, the result on .NET 8 x64 is expected to be int.MinValue (the pre-.NET 9 x86/x64 non-saturating conversion). The shipped exe is published as net8.0 win-x64. In that case _curTrace[int.MinValue] throws IndexOutOfRangeException. TelemetryReceiver.RunAsync calls Handle outside its inner try, and the outer try has only a finally, so the telemetry task faults and stops. The phone dashboard and engineer radio stop for the session, while pad input on :5555 keeps working. At shutdown, await Task.WhenAll(tasks) rethrows the exception, and the catch handles only OperationCanceledException, so it escapes async Main before the cleanup and Dispose lines run. Port 20777 binds all interfaces with no source check, and the firewall rule allows the exe on the Private profile, so any LAN peer can send the datagram. The packet needs a 2021 header with packetId 2, a full 22-entry Lap Data body, resultStatus >= 2 at the player entry, and a sessionTime that does not move backwards. Impact is availability only and limited to home-LAN scope, in line with the comparable LAN pad-mapper baseline.

**Claimed root cause:** There is no lower-bound (bin >= 0) or finiteness check on the lap-distance bin index (RaceTracker.cs:210-211), and RunAsync has no per-datagram exception containment around Handle (TelemetryReceiver.cs:150).

**Trace**
- entrypoint `windows-receiver/F1Controller/Validation/TelemetryReceiver.cs:130` (TelemetryReceiver.RunAsync): new UdpClient(20777) binds all interfaces, and any LAN peer the firewall lets through can send to it
- propagation `windows-receiver/F1Controller/Validation/TelemetryReceiver.cs:150` (TelemetryReceiver.RunAsync): Handle(result.Buffer) runs outside the inner try, and the outer try has only a finally
- propagation `windows-receiver/F1Controller/Validation/TelemetryReceiver.cs:262` (TelemetryReceiver.Handle): For format 2021 and packetId 2, the buffer goes to RaceTracker.Process
- propagation `windows-receiver/F1Controller/Validation/RaceTracker.cs:139` (RaceTracker.Process): lapDist is read as a raw little-endian f32 from the player's lap entry at offset 12
- propagation `windows-receiver/F1Controller/Validation/RaceTracker.cs:210` (RaceTracker.Process): bin = (int)(lapDist / 10f) is an unchecked conversion, expected to give int.MinValue for +Infinity or huge values on .NET 8 x64
- sink `windows-receiver/F1Controller/Validation/RaceTracker.cs:213` (RaceTracker.Process): _curTrace[bin] with a negative bin throws IndexOutOfRangeException, which faults the telemetry task

**Evidence**
- `windows-receiver/F1Controller/Validation/RaceTracker.cs:211`: The guard is lapDist >= 0 && bin < MaxBins - 1, with no bin >= 0
- `windows-receiver/F1Controller/Validation/TelemetryReceiver.cs:144`: The inner try catches only OperationCanceledException and SocketException around ReceiveAsync
- `windows-receiver/F1Controller/Program.cs:251`: The catch around await Task.WhenAll(tasks) handles only OperationCanceledException, so the faulted telemetry task's exception escapes Main at shutdown
- `windows-receiver/F1Controller/F1Controller.csproj:5`: TargetFramework is net8.0 and there is no CheckForOverflowUnderflow setting
- `installer/build.ps1:31`: The shipped exe is published as -r win-x64 self-contained, which is the x64 code path where pre-.NET 9 conversions do not saturate

**Blockers**
- The decisive runtime fact is the value of (int)(float.PositiveInfinity / 10f) in the JIT-compiled RaceTracker.Process on the net8.0 win-x64 runtime. ECMA-335 leaves an out-of-range conv.i4 unspecified. The .NET 9 'saturating floating-point conversions' change implies that .NET 8 x64 returns 0x80000000, but this was not observed because no OS-enforced sandbox is available, so no target code ran.

**Validation plan**
- Local: In a sandboxed net8.0 win-x64 xUnit test with no network: allocate a buffer of 24 + 22*43 bytes. ### 6. Elevated uninstaller runs {app}\FullLock.exe without ACL hardening when installed to a custom directory

**Fingerprint:** `installer/FullLock.iss:UninstallRun:elevated-exec-from-user-chosen-app-dir`

The installer requires admin (PrivilegesRequired=admin) and leaves the directory page enabled (no DisableDirPage, so Inno's default 'auto' shows it on a fresh install). Only DefaultDirName={autopf}\FullLock is set; there is no [Dirs] Permissions entry, no [Code] check that restricts {app} to Program Files, and no icacls step. The elevated uninstaller runs {app}\FullLock.exe --hidhide-cleanup ([UninstallRun] line 55). If the owner installs outside Program Files (for example C:\FullLock) and the inherited ACL gives non-admin users modify rights, another local standard user could replace FullLock.exe and have the admin's later uninstall run it elevated. Default installs to Program Files are not affected. The same writable-{app} condition also exposes the Inno uninstaller stub (unins000.exe) and the shortcuts in {app}, so line 55 is one instance of a broader install-directory-trust issue, not the only one. Severity is low: it needs a non-default install location, a second lower-trust local account and a later admin uninstall.

**Claimed root cause:** FullLock.iss trusts the integrity of {app} when running {app}\FullLock.exe elevated in [UninstallRun] (line 55). It neither restricts the install location to an admin-only parent nor sets admin-only permissions on {app}. Inno [Dirs] Permissions can only add grants, so a fix has to pin or validate the location (for example DisableDirPage=yes, or a NextButtonClick check that {app} is under {autopf}) or strip inherited user write access.

**Trace**
- entrypoint `installer/FullLock.iss:14` ([Setup] DefaultDirName): Only a default ({autopf}\FullLock) is set. DisableDirPage is absent, so the elevated installer's directory page accepts any path the installing admin chooses.
- propagation `installer/FullLock.iss:35` ([Files]): FullLock.exe is copied into {app}. Without a [Dirs] Permissions entry or an ACL step, it keeps the ACL inherited from the chosen parent.
- sink `installer/FullLock.iss:55` ([UninstallRun]): The elevated uninstaller executes {app}\FullLock.exe --hidhide-cleanup (runhidden, waituntilterminated).

**Evidence**
- `installer/FullLock.iss:17`: PrivilegesRequired=admin, so install and uninstall run elevated.
- `installer/FullLock.iss:55`: [UninstallRun] runs the binary from {app} elevated.
- `windows-receiver/F1Controller/Program.cs:71`: The --hidhide-cleanup branch is what the legitimate binary does. A substituted binary would run arbitrary code instead.

**Blockers**
- The effective ACL on a custom install directory such as C:\FullLockTest, created by elevated Inno Setup 6 on Windows 11, is an OS runtime fact that source cannot show. It decides whether a standard user can modify FullLock.exe. Source shows no hardening, and no sandbox is available to observe the ACL.
- Exploitation also needs the owner to pick a non-default directory, a second lower-trust local account on the PC, and a later admin uninstall.

**Validation plan**
- Local: On a disposable Windows 11 VM with one admin account and one dummy standard account: install FullLock-Setup as admin to C:\FullLockTest. Run icacls C:\FullLockTest and icacls C:\FullLockTest\FullLock.exe and record whether Users or Authenticated Users have M/W rights. If they do, sign in as the standard user and replace FullLock.exe with a benign marker binary that only writes whoami /groups output to C:\FullLockTest\marker.txt. Then uninstall as admin and check whether the marker shows the High Mandatory Level/admin group. Stop there. Repeat with the default {autopf} path as a negative control. Revert the VM afterwards.
